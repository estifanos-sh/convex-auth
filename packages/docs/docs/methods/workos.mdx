The WorkOS component and the `workos` sign-in method, in the
`@estifanos-sh/convex-workos` package, let your customers' employees sign in
with their company's identity provider (Okta, Entra ID, Google Workspace, any
SAML or OIDC IdP) through [WorkOS](https://workos.com), and keep a copy of
each customer's SCIM directory in your deployment, as WorkOS's own objects.

WorkOS only does SSO and Directory Sync here. Sign-in goes through WorkOS's
standalone SSO API, not AuthKit: WorkOS creates no users and no sessions of
its own, and the session is Convex Auth's like with every other method.

The profile passed to `createUser` and `onSignIn` is `vWorkosAccount(...)`:
WorkOS's own SSO profile with its own field names (the profile `id`, which
is the account id, `organization_id`, `connection_id`, `idp_id` and
`email`), and in `host` the host args of the call. The email is asserted by
the customer's identity provider and not verified by WorkOS, so don't use it
to link to an existing account unless its domain is one the organization
verified.

If your client passes extra args to every call, such as the site a sign-in
is for, declare them as `args: { siteId: v.id("sites") }`. Both
`startSignInWithWorkos` and `completeSignInWithWorkos` then take and
validate them, and the callbacks get the values of the completing call as
`method.profile.host`; declare the profile as
`vWorkosAccount({ siteId: v.id("sites") })`, and as `vWorkosAccount({})`
without host args. The React hook calls the functions with their own args
only, so a client that passes host args calls them itself.

To serve the callback from your app's own domain (e.g. a proxy that forwards
`https://app.example.com/workos/*` to the deployment's site URL), pass
`callbackUrl: () => "https://app.example.com/workos/callback"` and add that
URL as the redirect URI instead. `callbackUrl` and `allowedRedirectOrigins`
can both be functions, read when sign-in starts, so they can come from the
deployment's environment.

</Step>

## Deferred provisioning

An app that provisions its users asynchronously, through a workflow, a queue
or a directory sync, can't create the user inside the sign-in's transaction.
It attaches its callbacks with `attachProvisionedUserCallbacks`, which takes
a `provision` callback besides `createUser`. For an account with no user yet, `provision` runs first and answers `{ ready: true }` to create the
user now with `createUser`, or `{ defer: true }` to wait. It runs in the
sign-in's transaction, so it can file its provisioning work there. With
`attachUserCallbacks`, sign-in works as described above.

```ts
export const provision = internalMutation({
  args: vWorkosProvisionArgs({}),
  returns: vWorkosProvision,
  handler: async (ctx, { profile }) => {
    const user = await ctx.db
      .query("users")
      .withIndex("workosId", (q) => q.eq("workosId", profile.id))
      .unique();
    if (user !== null) return { ready: true as const };
    await ctx.scheduler.runAfter(0, internal.users.importWorkos, {
      workosId: profile.id,
    });
    return { defer: true as const };
  },
});
```

`createUser` then returns the id of the user the import made.

On `defer`, `completeSignInWithWorkos` mints no session: it keeps the
verified profile and the host args under a single-use ticket and returns
`{ status: "deferred", ticket }`. `finishSignInWithWorkos({ ticket })` asks
`provision` again with what it kept. On `ready`, it signs the user up through
`createUser` and spends the ticket; while `provision` still defers, it returns
the same ticket. `provision` runs again on each finish, so the work it files
must be idempotent. A ticket lives as long as an authorization request, ten
minutes from the sign-in; a spent or expired one returns `INVALID_CODE`.

The client registers the WorkOS package's own `workos()` in place of
`oauth()`, since both would claim the callback's code, and signs in with
`useProvisionedSignInWithWorkos`. Its `deferredTicket` holds the ticket of a
deferred sign-in, and `finish(ticket)` finishes it, as the example's sign-in
page above does every two seconds until the user exists:

```tsx file="examples/react-workos/src/main.tsx" title="src/main.tsx"

```

Deferred provisioning runs on the SPA session model only, not yet under the
SSR auth proxy: the proxy forwards only a session or an error, so its
`signIn` allowlist refuses the completion and the finish of a host that
provisions users, at compile time.

## Directory Sync (SCIM)

The component keeps a copy of the WorkOS environment: its organizations, their
domains, the SSO connections, the directories, and their users and groups, as
WorkOS's own objects with WorkOS's field names, tagged by their `object`.
There is no membership object: a directory user's roles are its own `role`
and `roles`, as WorkOS assigns them from the groups it is in.

The copy is kept from WorkOS's
[Events API](https://workos.com/docs/events), which lists every change in
order. `events.pull` (an action) fetches the next page, decodes it and stages
it in the component; `events.land` (a mutation) applies that page to the copy
and returns `{ landed: true, changes }`, each change a WorkOS event as a
typed union on `event`, or `{ landed: false }` for a page another sync
landed first. Run `land` in your own mutation, so your data changes in the
same transaction as the copy, and the two never disagree. The first pulls
fill an empty copy: they list everything WorkOS holds, as `*.created` and
`*.activated` changes, then follow the events from when the fill started. A deleted directory's users and
groups come back as `dsync.user.deleted` and `dsync.group.deleted` changes,
which WorkOS sends no event for.

Two pulls from the same place stage a page each, and only one of them lands,
so two syncs at once are harmless. A pull never conflicts with a landing: it
only inserts its page, which nothing a landing reads covers. The example
signs a user out everywhere when the directory deletes or deactivates them:

```ts file="examples/react-workos/convex/workos.ts" title="convex/workos.ts"

```

Pull whenever you want the copy current: after a deploy, before a sign-in, or
when WorkOS rings. A webhook endpoint in the WorkOS dashboard can ring a sync,
as the example's `/ring` route does; the delivery carries nothing the sync
trusts, because the sync reads the events from WorkOS's API with the API key.
WorkOS keeps events for 90 days: a deployment idle longer runs
`events.reset` until it returns `done`, and the next pull fills the copy
again.

The component's queries read the copy, one module per object:
`organizations.get` (`by: { id }`, or `by: { externalId }` for the external id
your app set on the organization to link it to its own entity) and `list`,
`organizationDomains.get` (by domain or email) and `list`, `connections.get`
and `list`, `directories.get` and `list`, `directoryUsers.get` and `list`
(filtered by `directory`, by `organization` and optionally `idpId`, which an
SSO profile carries too, by `idpId` or by `email`), and `directoryGroups.get`
and `list` (by `directory` or `organization`).

## Admin Portal

Your customer's IT admin sets up their SSO connection, their SCIM directory
and their domain in WorkOS's Admin Portal. The component's
`portal.link` action returns a short-lived link for one organization
and an intent (`sso`, `dsync`, `domain_verification` or
`certificate_renewal`). It does no authorization: check that the caller
administers that organization first.

```ts
export const adminPortal = action({
  args: { organizationId: v.string() },
  handler: async (ctx, { organizationId }) => {
    // Check that the caller administers `organizationId` here.
    return await ctx.runAction(components.authWorkos.portal.link, {
      organizationId,
      intent: "sso",
      returnUrl: "https://app.example.com/settings",
    });
  },
});
```
