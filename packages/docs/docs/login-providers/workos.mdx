The WorkOS component and the `workos` sign-in method let your customers'
employees sign in with their company's identity provider (Okta, Entra ID,
Google Workspace, any SAML or OIDC IdP) through
[WorkOS](https://workos.com), and keep a copy of each customer's SCIM
directory (users, groups and memberships) in your deployment.

WorkOS only does SSO and Directory Sync here. Sign-in goes through WorkOS's
standalone SSO API, not AuthKit: WorkOS creates no users and no sessions of
its own, and the session is Convex Auth's like with every other method.

The profile passed to `createUser` and `onSignIn` is `vWorkosProfile`: the
WorkOS profile id (the account id), the `organizationId`, the `connectionId`,
the `idpId` and the email. The email is asserted by the customer's identity
provider and not verified by WorkOS, so don't use it to link to an existing
account unless its domain is one the organization verified.

To serve the callback from your app's own domain (e.g. a proxy that forwards
`https://app.example.com/workos/*` to the deployment's site URL), pass
`callbackUrl: () => "https://app.example.com/workos/callback"` and add that
URL as the redirect URI instead. `callbackUrl` and `allowedRedirectOrigins`
can both be functions, read when sign-in starts, so they can come from the
deployment's environment.

## Directory Sync (SCIM)

The component keeps a copy of the environment's organizations, verified
domains, SSO connections, directories, directory users, groups and
memberships. Webhook deliveries keep it current: a verified delivery names
an object, which the webhook reads again from WorkOS and writes as it is
now, or removes if WorkOS answers 404. WorkOS delivers in no guaranteed
order, and reading the current state makes the order not matter. A
membership delivery lists the group's members again in the background, and
a deleted directory, user or group loses its contents a batch at a time.

`setupWorkosDirectory` takes your handler, an internal mutation that runs
for each change in the same transaction that applies it. Map directory users
and groups onto your own users and roles there. A `user` change with
`deprovisioned: true` means the directory deleted the user or marked them
inactive: revoke their sessions.


`registerWorkosWebhook` registers the deployment's webhook endpoint,
`<site-url>/workos/webhook`, at WorkOS through the
[Webhooks API](https://workos.com/docs/reference/webhooks), subscribed to the
events the copy keeps, and keeps in the component the secret WorkOS signs
its deliveries with and your handler. It finds the endpoint by its URL, so it
never creates a second one, and it enables the endpoint again if WorkOS
disabled it. Until it has run, the webhook refuses every delivery.

`reconcileWorkosDirectory` lists everything WorkOS holds, a page per
mutation in the background, and writes each object the same way. A row the
listings no longer show is read again by id and removed only if WorkOS
answers 404, so overlapping runs are harmless. A 429, a 5xx or a timeout
makes it wait and try the same step again. It fills a new deployment's copy and
repairs deliveries the webhook missed: WorkOS retries a failed delivery for
a few minutes in staging and for up to 3 days in production. Run both after
every deploy:

```sh
npx convex run workos:registerWorkosWebhook
npx convex run workos:reconcileWorkosDirectory
```

Every deployment that shares a WorkOS environment, such as a preview
deployment, registers its own endpoint, and WorkOS keeps an endpoint after
its deployment is gone. Run `unregisterWorkosWebhook`, which deletes this
deployment's endpoint and its secret, before you delete the deployment:

```sh
npx convex run workos:unregisterWorkosWebhook
```

A handler that throws refuses the delivery, and WorkOS retries it; in a
reconcile, it stops the run at that step, and the next reconcile tries again.

The component's `directory` queries read the copy: `route`,
`getOrganization`, `listDirectories`, `getUser`, `findUsers` (by
`organizationId` and `idpId`, which an SSO profile carries too), `listUsers`,
`listGroups`, `listUserGroups` and `listMembers`.

## Admin Portal

Your customer's IT admin sets up their SSO connection, their SCIM directory
and their domain in WorkOS's Admin Portal. The component's
`portal.generateLink` action returns a short-lived link for one organization
and an intent (`sso`, `dsync`, `domain_verification` or
`certificate_renewal`). It does no authorization: check that the caller
administers that organization first.

```ts
export const adminPortal = action({
  args: { organizationId: v.string() },
  handler: async (ctx, { organizationId }) => {
    // Check that the caller administers `organizationId` here.
    return await ctx.runAction(components.authWorkos.portal.generateLink, {
      organizationId,
      intent: "sso",
      returnUrl: "https://app.example.com/settings",
    });
  },
});
```
